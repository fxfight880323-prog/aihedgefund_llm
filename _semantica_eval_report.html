Semantica 适配度评估 — ai_fund_framework

2026-09-04 · 实测驱动 · 中文金融 quant workspace

核心结论: Semantica 不适合这个 workspace。 它的设计目标是英文 GraphRAG,normalize 三模块对中文金融文本几乎零支持。 只有 HTMLParser 真能用;真要做"组织",推荐更轻量的轻量栈(markitdown + bge-m3 + ChromaDB)。

1. 评估背景

目标:判定 Semantica(pip install semantica 0.6.7)能否用于组织 ai_fund_framework 这个 A 股量化研究工作空间。

现状:650 个根目录文件,~400 个 _*.py、~30 个 _*_report.html、若干巨型 JSON dump(35MB/73MB)、一个 SQLite(data/a_share_market.db)。 知识层在 Obsidian vault(D:\Fortune\量化研究\)里已成体系。

试点方法: 7 项实测(_semantica_pilot.py),覆盖 parse/normalize 的中文金融场景。

DateNormalizer
6 种日期格式		 有 bug ISO/英文格式 ✅;中文/不完整有 bug:
"2024-01-15" → 2024-01-15T00:00:00+00:00 ✅ "2024/01/15" → 2024-01-15T00:00:00+00:00 ✅ "2024.01.15" → 2024-01-15T00:00:00+00:00 ✅ "15-Jan-2024" → 2024-01-15T00:00:00+00:00 ✅ "2024年1月15日" → 2026-09-04T19:04:31.188901+00:00 ❌ 错认为"今天" "2024-01" → 2024-01-04T00:00:00+00:00 ❌ 错误补充日

5. 三条下一步路径

路径 A — 改用轻量栈(推荐)

栈 markitdown + bge-m3(本地) + ChromaDB / sqlite-vec

工程量 ~3 天

优势 中文友好、零对 Semantica 中文坑、依赖轻量(无 torch)、查询延迟低

解决 痛点 1(跨报告找结论)100% + 痛点 2(实体名)80%

路径 B — 引 Semantica,自写中文层

栈 Semantica HTMLParser / KG + 自写 entity/dict/num cn 层

工程量 ~5-7 天

优势 在 Semantica 的 KG / pipeline / core 框架上搭,后续有 reasoning 潜力

劣势 自写量 > Semantica 现成价值,等于把 normalize 重写

路径 C — 只用 Semantica 的"骨架"

栈 只用 pipeline + core 的 DAG 编排能力

工程量 1-2 天集成

适用 把 run.py 迁到 Semantica pipeline 框架

边际价值 run.py 的 5 个 step 已经能跑,DAG 化收益有限

6. 关键技术决策

如果走路径 A,关键参数:

组件选型理由
文档→markdownmarkitdownMicrosoft 出品、HTML/CSV/PDF 全支持、中文友好
embedding 模型bge-m3 或 bge-large-zh-v1.5中文 SOTA、本地 0.6-1.3GB、可离线
向量库ChromaDB(嵌入式)或 sqlite-vec(嵌入 SQLite)不引入 Neo4j 这种独立服务,落盘随项目走
实体对齐自维护 _entity_map.json(A 股核心 ~200 只)Semantica EntityNormalizer 不可用,自己 1 天写完
中文数字归一jionlp 或 1 个 regex补 Semantica NumberNormalizer 的坑
旧 vs 新结论冲突报告 YAML frontmatter 标 effective_from / supersedesSemantica conflicts 模块是工程级 overkill
